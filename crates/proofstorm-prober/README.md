# Prober architecture and scale investigation

Status: the persistent worker and watch-backed controller integration pass the isolated Kubernetes connection, fairness, recovery and freshness checks below. Further full-fleet resource and application-interference measurements remain before making capacity claims. The running user installation has not been upgraded.

## Problem and evidence

At source revision `774f375`, a cell has one prober Deployment containing one BusyBox container per probed component. Each container sleeps between kubelet exec readiness checks. The five-second period, two-second timeout and per-container resource requests mean 150 targets configure 150 containers, 750m CPU and 600 MiB of memory requests for probing alone. Requests are scheduling reservations, not measured utilization.

The previous isolated 150-component experiment exposed controller status-size rejection and a stalled, expensive prober Pod teardown. The revised controller observed all 150 component identities but that constrained node never reached full readiness. Those results establish observability and recovery improvements; they do not measure the prober's independent CPU cost or demonstrate a healthy 150-node fleet. See [the MCP campaign](../../dev/MCP-AGENT-RESULTS-2026-09-12.md).

The previous scheduler rotated whole prober Deployments among cells, wrote a lease into the Pod template and waited for outgoing Pods to disappear before activating other cells. This makes scheduling a workload lifecycle operation. A slow teardown can delay checks elsewhere. Full-cluster list operations every two seconds add control-plane work even when nothing changed.

## Research and resulting choices

Sources accessed September 12, 2026. The choices below are our application of the sources, not claims that Kubernetes or Prometheus endorses this particular implementation.

| Primary source | Relevant guidance | Application to Proofstorm |
|---|---|---|
| [Kubernetes probe mechanisms](https://kubernetes.io/docs/concepts/workloads/pods/probes/) | Exec probes create/fork processes and can impose CPU overhead at high density or short intervals. | Replace repeated commands with direct asynchronous TCP/HTTP checks in a persistent worker. |
| [Prometheus multi-target exporter pattern](https://prometheus.io/docs/guides/multi-target-exporter/) | A persistent exporter accepts targets, performs network checks from its own location and returns results. | Keep execution near the cell and schedule targets independently of worker Pod lifecycle. |
| [Prometheus Operator blackbox integration](https://github.com/prometheus-operator/kube-prometheus/blob/main/docs/blackbox-exporter.md) | `Probe` resources describe checks performed by a blackbox exporter. | This is an established Kubernetes pattern. We need neither a Prometheus installation nor a time-series database to adopt its separation of scheduler and prober. |
| [Blackbox exporter configuration](https://github.com/prometheus/blackbox_exporter/blob/master/CONFIGURATION.md) | Timeouts, HTTP status acceptance, redirect policy and address-family selection are explicit probe semantics. | Define those semantics, distinguish execution failure from target failure, and test them. The prototype accepts HTTP 2xx headers, follows no redirects and reads no response body. |
| [Blackbox handler implementation](https://github.com/prometheus/blackbox_exporter/blob/master/prober/handler.go) | Probes execute with a request-derived deadline and report success separately from duration. | Bound the entire check including DNS and connection time; return structured outcomes and elapsed time. |
| [Kubernetes efficient change detection](https://kubernetes.io/docs/reference/using-api/api-concepts/#efficient-detection-of-changes) | List/watch and resource versions support a synchronized local cache. | Maintain six shared resource watches and route changes to their cell, rather than repeatedly listing the fleet for scheduling. A watch failure invalidates eligibility until its complete relist finishes. Kubernetes copies nonreserved Service labels to EndpointSlices, allowing the same instance label selector on that watch: [upstream implementation](https://github.com/kubernetes/endpointslice/blob/master/utils.go#L195). This propagation was also verified on the isolated Kubernetes v1.34.9 cluster. |
| [Kubernetes Service DNS](https://kubernetes.io/docs/concepts/services-networking/dns-pod-service/) | Service discovery is namespace scoped, search lists expand names, and the cluster domain is configurable. | Resolve absolute Service names using the actual Pod DNS configuration. Preserve the cell's network vantage without assuming `cluster.local`. |
| [Tokio blocking-task cancellation](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html), [Hickory system resolver](https://docs.rs/hickory-resolver/0.25.2/hickory_resolver/type.TokioResolver.html) | Started blocking tasks cannot be aborted; an asynchronous resolver can read system DNS configuration. | Use asynchronous DNS, bounded deadlines and no application DNS cache. A timed-out check must not accumulate blocked resolver threads. |

## Candidate architecture

One persistent, restricted worker per cell accepts small batches from a fair controller scheduler. Batches limit concurrent work, not the number of targets a cell can contain. The worker accepts batches of up to 32 targets and permits four concurrent batches (128 checks) across six transport connections. The pure scheduler permits eight batches globally (256 requested checks); the controller now uses this scheduler. These defaults must be assessed against measured latency, CPU, memory and freshness under failure.

The worker has no Kubernetes token, custody storage, shell commands or user-supplied credentials. It accepts component names rather than arbitrary target URLs, constructs their Service DNS names inside its own namespace, and rejects an entire invalid batch before network work. It does not use environment HTTP proxies or follow redirects to other hosts. TCP establishes a connection; HTTP requires a 2xx status. These are reachability checks, not proof that an authenticated RPC or transaction will succeed.

The prototype transport is bounded, length-prefixed JSON on loopback, reached through Kubernetes authenticated port-forward. This preserves the existing authorization boundary and works for a host-run development controller. It is **not yet a validated fleet-scale transport choice**: measure connection establishment and API-server load, compare connection reuse, and replace it with authenticated direct in-cluster transport if the control plane becomes the bottleneck. Probe requests carry no target response bodies.

Protocol v2 makes connection lifetime explicit. Ordinary scheduler requests set `keep_alive: false`; the worker closes its socket immediately after writing the reply. A measurement client can explicitly request reuse. The six-connection limit and four-batch limit remain unchanged. The version change prevents an older worker from silently retaining connections under the new controller's assumption.

Every result includes component and rollout identity, batch/revision identity, duration and monotonic age within the batch. The controller must bind accepted observations to the current cell incarnation and worker Pod UID and expire them. Worker unavailable, overdue, invalid or cancelled observations become Unknown. Old success must never authorize a changed component. Recheck action admission and client projections as well as controller status; merely adding timestamps to a report is insufficient.

Controller integration must also gate dispatch on the *observed current workload*, not just attach the desired rollout string to a request. An echo of a desired revision cannot prove that a still-old Service endpoint was replaced. Runtime endpoint/Pod identity and eligibility changes must invalidate the affected target. Incremental registration must preserve unaffected targets and their due times; repeatedly resetting a whole cell when one target flaps would cause starvation. Incremental registration now preserves unaffected observations and due times, while per-target generations reject late replies after removal or replacement.

Scheduling should rotate bounded batches while workers remain alive. A cell that has many failed targets cannot monopolize all slots or stop another cell being checked. Closing or replacing a cell cancels its work without a global teardown barrier. Stable results should not cause a complete workload reapply for every batch; observation updates and desired-resource reconciliation need separate paths or coalescing.

## Application quota isolation

Probe traffic must leave application request, authentication and payment quotas unchanged. Lower frequency alone cannot establish this: a read-only GET can still consume a global HTTP quota. Backend authors must audit both the remote protocol probe and local readiness in the pinned implementation, and repeat that audit when changing versions or candidate images. The worker cannot infer an endpoint's limiter behavior from its URL.

## Initial local measurements

These are unoptimized native macOS worker builds, with an owned local DNS server and cheap TCP/HTTP endpoints. The worker runs in a separate process; CPU and peak RSS come from that process's `wait4` usage. Fixtures and transport are loopback. They do not measure Kubernetes, CRI, real Lightning-node behavior, release-build performance, or full-controller overhead. Healthy cases use three sweeps spaced five seconds apart; timeout cases use one sweep. Every requested observation was returned and every worker exited cleanly.

| Test | One batch active | Four batches active |
|---|---:|---:|
| 1,000 healthy TCP targets, median sweep | 0.251 s | 0.228 s |
| 1,000 healthy HTTP targets, median sweep | 0.345 s | 0.303 s |
| 150 stalled HTTP targets, complete sweep | 10.035 s | 4.014 s |
| 1,000 stalled HTTP targets, complete sweep | 64.224 s | 16.100 s |
| Peak worker RSS, 1,000 stalled targets | 9.77 MiB | 16.81 MiB |
| Peak simultaneous endpoint connections, stalled case | 32 | 128 |

The one-batch design missed the proposed 30-second freshness window for a large failed cell despite excellent healthy-target latency. Four bounded batches provide headroom without changing cell admission. Small and large cells still share a fair queue. Under workloads that exceed sustainable probe throughput, expired observations must become Unknown; concurrency is not a guarantee of arbitrary fleet size at a fixed interval.

These first measurements used Reqwest. Inspection then found its underlying HTTP/1 response-buffer default was approximately 400 KiB and was not exposed through that client builder. The next worker iteration uses Hyper directly, explicitly bounds response buffering to 16 KiB / 64 headers, and drives each connection in the check's own cancellable future. See [Hyper's documented buffer and header controls](https://docs.rs/hyper/latest/hyper/client/conn/http1/struct.Builder.html). This also avoids detached HTTP connection tasks and connection pooling. The bounded implementation passes 15 network/protocol/scheduling regressions and Clippy with warnings denied. The final bounded implementation returned all 7,600 observations across the same five benchmark cases. Median 1,000-target sweeps were 0.215 s for TCP and 0.252 s for HTTP. The complete 1,000-timeout sweep remained 16.098 s with a measured peak of 128 endpoint connections and 13.73 MiB worker RSS. The healthy HTTP case used 13.28 MiB peak RSS and 0.735 worker CPU seconds over three sweeps, compared with 17.58 MiB and 0.887 CPU seconds in the preceding four-batch Reqwest run. These are small local comparisons, not a Kubernetes capacity promise or a statistical performance guarantee.

Final raw evidence: `worker-bench/results-four-batches-bounded-http.json` in the same temporary campaign. Three iterations produced 22,800 observations; all benchmark workers were reaped with exit 0. The source snapshot and hashes are recorded alongside them. No installed binaries or Kubernetes resources changed.

Raw initial evidence: `/private/tmp/proofstorm-prober-scale-20260912-xn4bb04d/worker-bench/results-one-batch.json` and `results-four-batches-reqwest.json`. All benchmark workers and fixtures from those runs have stopped.

## Controller integration checks

The controller now separates cached readiness reconciliation from resource application. A focused fake-API regression verifies the readiness path performs only a changed-status write and suppresses an identical repeat; it performs no resource list or workload write. Desired resources still receive periodic reconciliation, so full-controller scale measurements must include that cost. Large-cell measurements must also include controller CPU and watch-event bursts, rather than extrapolating from worker-only throughput.

An in-memory benchmark then confirmed quadratic resource lookup cost within a cell. Component status projection took approximately 19 ms for 100 independent Bitcoin components, 1.55 s for 1,000, and 6.76 s for 2,000. The controller uses a bulk eligibility entry point so it shares the same index across all targets. Input order and every matching EndpointSlice are retained; the index does not clone Kubernetes resource objects.

### Transport failure and validation

A 1,000-target Kubernetes experiment exposed a transport-lifecycle failure that direct socket tests did not: six sequential batches completed, then the seventh new connection returned `UnexpectedEof`, with the worker still Ready and zero restarts. Explicitly shutting down the client's duplex stream and waiting for the Kubernetes WebSocket to close had the same result. This is consistent with delayed downstream connection cleanup; the exact failing Kubernetes layer has not been identified. Protocol v2 now closes the worker end after an ordinary reply, so slot release does not rely on tunnel teardown. The new regression retains 18 completed client sockets and also checks explicit reuse.

The original worker successfully returned 3,000 HTTP observations over reused connections, with three 1,000-target sweeps of 0.378, 0.378 and 0.383 seconds.
